# CNGX1015

## Non-modal dialog without a live region

This warning is emitted when a `<dialog cngxDialog>` opens as a non-modal dialog and no element with `aria-live` sits next to the element that opened it.

A modal dialog (`showModal()`) moves focus into itself, so a screen reader lands in the dialog and reads it. A non-modal dialog (`show()`, `[modal]="false"`) leaves focus on the trigger: the page behind it stays interactive, which is the point of a non-modal dialog. The dialog appears visually, but nothing tells a screen reader user that it did.

At `open()`, `CngxDialog` remembers the focused element as the trigger and looks for an `aria-live` region among the trigger's siblings. It finds none, so the dialog opens unannounced:

```html
<!-- WARNING: nothing near the trigger announces the dialog -->
<div class="toolbar">
  <button type="button" (click)="filters.open()">Filters</button>
</div>

<dialog cngxDialog #filters="cngxDialog" [modal]="false">
  <h2 cngxDialogTitle>Filters</h2>
  ...
</dialog>
```

### Fixing the warning

#### Option 1: Announce the dialog next to its trigger

Put a polite live region in the trigger's parent and write a short message into it when the dialog opens:

```html
<div class="toolbar">
  <button type="button" (click)="filters.open()">Filters</button>
  <span aria-live="polite" class="sr-only">
    {{ filters.lifecycle() === 'open' ? filtersOpenedLabel() : '' }}
  </span>
</div>
```

The region must be in the DOM before the dialog opens; a live region that appears together with its text is not announced reliably. Route the message through your own i18n, like any other copy.

#### Option 2: Open the dialog as modal

If the dialog asks for input before the user continues, it is a modal dialog. Drop `[modal]="false"`: focus moves into the dialog, and the screen reader reads it.

### Debugging the warning

The message names the dialog by its id, for example `CngxDialog [cngx-dialog-3]`, which is the `id` attribute on the `<dialog>` element. Search the rendered DOM for that id to find the dialog.

The check runs in development mode only, once per `open()`, and looks only at the parent of the element that had focus when `open()` ran. If the dialog opens from code (a timer, a route change), the focused element may not be the button you think of as the trigger; the region has to sit next to whatever had focus.
