# CNGX3013

## Alternate placement ignored in an activity timeline

This warning is emitted when a `<cngx-timeline>` has `placement="alternate"` together with `mode="activity"`.

The two inputs describe different layouts. `mode="activity"` is the feed raster: the timestamp trails the body on one line, and the list is meant to be scanned top to bottom along one edge. `placement="alternate"` centres the rail and flips each row to the other side, the infographic layout for a narrative history. Alternating sides in a feed forces the eye to zigzag and defeats the scan, so cngx does not support the combination: in activity mode every row is placed on the start side, and the styles that centre the rail for `alternate` are scoped to non-activity timelines.

The timeline renders without errors, but as a single-sided feed. The `placement` binding has no effect, which is easy to mistake for a styling bug when the timeline is wide enough to alternate.

```html
<!-- WARNING: alternate placement is ignored in activity mode -->
<cngx-timeline [items]="events()" [dateAccessor]="at" mode="activity" placement="alternate">
  ...
</cngx-timeline>
```

### Fixing the warning

#### Option 1: Use the narrative mode to alternate

If the alternating layout is what you want, switch to `mode="narrative"` (the default):

```html
<cngx-timeline [items]="milestones()" [dateAccessor]="at" placement="alternate">
  ...
</cngx-timeline>
```

#### Option 2: Pick a single side for the feed

If the timeline is a feed, keep `mode="activity"` and drop `placement`, or set it to `'start'` (the default) or `'end'` to mirror every row.

### Debugging the warning

The message reads `[cngx-timeline] placement="alternate" is ignored in mode="activity"`. It does not identify the instance; search for timelines that bind both inputs, including bindings driven by a signal or a config object.

The check runs in development mode only, once per timeline, after the first render. It reads both inputs at that moment, so switching either input at runtime into this combination is not reported. The row placement itself is derived on every render, so the behaviour (start side in activity mode) holds whether or not the warning fired.
