# CNGX2011

## Filter path runs through an expression

This error is thrown when a `createFilterBuilderState` mutator from `@cngx/forms/filter-builder` receives a path that treats an expression as a group: either the path continues below an expression, or it asks to append a child to one.

The filter builder stores its tree as nested `FilterGroup` and `FilterExpression` nodes and addresses a node by a path of child indexes: `[]` is the root group, `[2, 0]` is the first child of the root's third child. Only groups have children. An expression is a leaf, so `[0, 1]` is meaningless when `[0]` is an expression, and `addExpression([0], ...)` or `addGroup([0], ...)` has nowhere to put the new node. The mutator throws instead of guessing a parent.

```typescript
// the root's first child is an expression
state.setValue([0, 1], 'Vienna'); // ERROR: cannot descend into expression at [0]
state.addExpression([0], expression); // ERROR: cannot append to non-group at [0]
```

### Fixing the error

Append to a group: pass the group's path, `[]` for the root. To put a new condition next to an expression, append to the expression's parent, which is its path without the last index.

```typescript
state.addExpression([], expression); // next to the root's expressions
```

To turn one condition into a nested group, add a group that contains it and remove the original, or add the group first and then the expressions into it at the group's path.

### Debugging the error

The message names the operation: `CNGX2011: updateAtPath(): cannot descend into expression at <path>` gives the part of the path that ended at the expression; `CNGX2011: appendAtPath(): cannot append to non-group at <path>` gives the expression's path. In a production build the message is the bare code `CNGX2011`; the check still runs there.

A path that was valid when it was built can point at an expression later, after a removal shifted the indexes. Check the node with `state.getNodeAtPath(path)` right before the call.
