# CNGX2001

## Unknown filter operator

This warning is emitted when the filter builder evaluates a `FilterExpression` whose `operator` key has no registered definition: it is neither one of the builtins in `CNGX_FILTER_BUILTIN_OPERATOR_DEFS` (`eq`, `contains`, `gt`, `between`, `in`, ...) nor a key added with `withOperators`.

An operator key is only a name. What it means at evaluation time comes from a `CngxFilterOperatorDef` and its `evaluate` function, looked up in the operator registry. Listing a key in `FilterFieldDef.operators` or `withDefaultOperators` only puts it into the row's operator picker; it does not tell the builder how to test an item against it.

Without a definition, `evaluateExpression` returns `false` for every item. In an `and` group one such row excludes everything, so the filtered list comes back empty and nothing in the UI says why. The picker itself shows the key under the generic "unnamed operator" label, because it has no label to show either.

```ts
const fields: FilterFieldDef[] = [
  {
    key: 'name',
    label: this.labels.name, // copy comes from your own i18n
    editorType: 'string',
    // WARNING: 'matches' is in the picker but has no evaluate function
    operators: ['contains', 'eq', 'matches'],
  },
];
```

### Fixing the warning

#### Option 1: Register the operator with `withOperators`

Give the key an `evaluate` function. `withOperators` merges over the builtins, so the existing operators keep working:

```ts
import { provideFilterBuilderConfig, withOperators } from '@cngx/forms/filter-builder';

provideFilterBuilderConfig(
  withOperators({
    matches: {
      evaluate: (itemValue, exprValue) =>
        typeof itemValue === 'string' &&
        typeof exprValue === 'string' &&
        new RegExp(exprValue).test(itemValue),
    },
  }),
);
```

Add `label` to the definition for the picker entry, or set `operators.matches` through `withFilterBuilderI18n`; the i18n entry wins. Set `valueless: true` for operators that need no value, like `isEmpty`.

#### Option 2: Correct or migrate the stored key

If the key is a typo, or comes from a saved filter written before an operator was renamed, fix the key in `FilterFieldDef.operators` or migrate the stored `FilterGroup` when you load it.

### Debugging the warning

The message quotes the key, for example `CNGX2001: evaluateExpression(): unknown operator "matches"`. The warning fires once per key for the lifetime of the application, however many items or rows evaluate it, so one line means one key.

The check runs in development mode only, at evaluation time, not at render. A row whose value is still empty is a no-op that evaluates `true` before the operator is looked up, so the warning appears only once the user fills in a value. A row whose `field` is unknown evaluates `false` before the operator is looked up as well; that case is [CNGX2003](cngx2003.html).

The `predicate` signal on the builder evaluates against the operator registry from `CNGX_FILTER_BUILDER_CONFIG`. If you call `toFilterPredicate` or `evaluateExpression` yourself, pass that registry in `options.operators` (for example `injectFilterBuilderConfig().operators`); without it they resolve against the builtins only, and every key registered with `withOperators` reports as unknown. The same happens when `provideFilterBuilderConfigAt` registers the operator on a component injector that is not an ancestor of the builder.
