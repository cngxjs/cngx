# CNGX3004

## Raw error text shown as error detail

This warning is emitted the first time a feedback surface appends the raw text of an error as its detail because the app has no `withErrorDetail` mapping. The surfaces are `CngxAlertOn`, `CngxToastOn` and `CngxBannerOn` with their `alertErrorDetail` / `toastErrorDetail` / `bannerErrorDetail` input set, and `CngxActionButton` with `toastErrorDetail` set.

Each of these resolves its detail through `injectErrorDetail()`. When `provideFeedback()` carries a `withErrorDetail(map)` feature, that function decides. Without it, the default differs by build: development builds return the error's `message` (or the thrown value when it is a string) so you can see what failed while building the UI, and production builds return nothing. The warning marks that difference.

Raw error text is written for developers: an HTTP status line, an English server message, a fragment of a stack. It is not translated and may expose internals. A UI that looks right in development, with a detail under every error, ships without those details, and nothing in development tells you so except this warning.

```html
<!-- WARNING: no withErrorDetail(...) in provideFeedback(), so the detail is err.message -->
<form [cngxToastOn]="submitState" [toastError]="submitFailedLabel()" [toastErrorDetail]="true">
  ...
</form>
```

### Fixing the warning

#### Option 1: Map errors to user-facing text

Add `withErrorDetail` to `provideFeedback()`. The function receives the error and returns the detail, or `undefined` to show the message alone:

```ts
provideFeedback(
  withToasts(),
  withErrorDetail((error) =>
    error instanceof HttpErrorResponse && error.status === 409 ? conflictDetail() : undefined,
  ),
);
```

Return text from your own i18n. The surface joins message and detail through `errorWithDetail(message, detail)` in `CNGX_FEEDBACK_I18N`, so the locale controls the order and separator.

#### Option 2: Drop the detail

If the bound error message is enough, remove the `*ErrorDetail` input. Development and production then render the same message.

### Debugging the warning

The message does not name a component; it starts with `CNGX3004: injectErrorDetail()`. Look for the first error transition on a surface that has an `*ErrorDetail` input set.

The check runs in development mode only, when a detail is actually resolved: on an `error` transition with the detail input set and a non-null error. It fires once per environment injector, so once per application, plus once per lazy-loaded route that creates its own environment injector. Later surfaces stay silent even though they also show raw text.

The default extracts text only from `Error` instances and plain strings. An `HttpErrorResponse` is neither (it implements `Error` but does not extend it), so it produces no detail and no warning even in development; map it with `withErrorDetail` if you want one.
