# CNGX0007

## Preference axis installed below the root injector

This warning is emitted when one of the theming preference installers from `@cngx/core` (`provideDensity`, `provideTextScale`, `provideMotion`, `provideContrast`, `provideTouchTargets`, or `provideA11yPreferences`, which calls them) runs in a child environment injector, such as a lazy route's `providers`, instead of the application config.

Each axis reflects its value onto one attribute of `<html>` (`data-density`, `data-text-size`, `data-motion`, `data-contrast`, `data-touch`). The document has one `<html>`, so one injector owns it: the root. A child install writes nothing to `<html>`, ignores its own initial value, and hands out the root signal, so every reader in the subtree sees the same value the document shows. Nothing throws; the child call simply has no effect.

```ts
export const routes: Routes = [
  {
    path: 'reports',
    // WARNING: does not make the reports area compact
    providers: [provideDensity('compact')],
    loadChildren: () => import('./reports/routes'),
  },
];
```

### Fixing the warning

#### Option 1: Set the preference for the whole app

Call the installer once in the application config and change the value at runtime through the signal:

```ts
bootstrapApplication(App, { providers: [provideDensity('comfortable')] });

// later, for example from a settings panel
injectDensity().set('compact');
```

#### Option 2: Change one subtree

Use the axis directive on the subtree's host element. It sets the attribute on that element, and the token CSS scopes the change to its descendants: `cngxDensity` (`CngxDensity`), `cngxMotionScope` (`CngxMotionScope`), `cngxContrast` (`CngxContrast`) and `cngxTouchTarget` (`CngxTouchTarget`).

```html
<section cngxDensity="compact">...</section>
```

### Debugging the warning

The message names the installer and the attribute, for example `CNGX0007: provideDensity() in a child injector does not write <html data-density> and shares the root signal`. Search the code for that installer; every call outside the application config is a candidate. Route `providers` and `createEnvironmentInjector` calls are the usual places.

The check runs in development mode only, through an environment initializer, so it fires once each time a child environment injector with the call is created. It compares that injector with `ApplicationRef.injector` and nothing else; a call in the application config never warns. The root-only behaviour itself (no write to `<html>`, the shared root signal) also applies in production.
