# CNGX1059

## Commit action completed without a decision

This error is stored, not thrown, when the `[commitAction]` of a stepper (`[cngxStepper]`, `<cngx-stepper>`) or a tab group (`[cngxTabGroup]`, `<cngx-tab-group>`) returns an Observable that completes without emitting a value.

A commit action decides whether a step or tab change goes through: it receives the current and the target index and answers `true` (move), `false` (stay), or a `Promise` / `Observable` of that answer. While the answer is pending the change is `pending` and the stepper or tab group is busy. An Observable that completes without a value, such as `EMPTY`, a `filter()` that drops everything, or an HTTP call mapped with `switchMap(() => EMPTY)`, never answers. Instead of staying busy forever, the stepper or tab group treats the completion as a failed commit: the change does not happen, the commit state moves to `error`, and its `error()` holds this `CngxRuntimeError`.

```typescript
// ERROR: the save stream completes without emitting when nothing changed
protected readonly saveStep = (from: number, to: number) =>
  this.api.save(this.draft()).pipe(filter((result) => result.changed));
```

### Fixing the error

Make the Observable always emit exactly one boolean, `true` to move on and `false` to stay:

```typescript
protected readonly saveStep = (from: number, to: number) =>
  this.api.save(this.draft()).pipe(map(() => true));
```

For a stream that may legitimately produce nothing, supply the decision yourself, for example with `defaultIfEmpty(true)` when an empty result means "nothing to save, move on".

### Debugging the error

The stored error's message reads `CNGX1059: [cngxStepper] commitAction completed without emitting true or false.`, or `[cngxTabGroup]` for tabs. In a production build the message is the bare code `CNGX1059`; the error is still stored there.

What a user sees depends on what renders the commit state. With `@cngx/ui` feedback bridges (`CngxAlertOn`, `CngxToastOn`, `CngxBannerOn`) reading the stepper or tab group, the error detail comes from `withErrorDetail(...)`. Without a mapping, a development build shows the raw message and a production build shows no detail. Code that inspects the error, such as a custom `withErrorDetail` mapping or a logger, should branch on `err instanceof CngxRuntimeError && err.code === 'CNGX1059'` instead of the text, because the text differs between development and production.

A commit action that answers `false` is a different case and stores no error at all: the change is refused on purpose, the commit state goes back to `idle` with its data, and `lastOutcome()` on the stepper or tab group reads `kind: 'refused'`. Only a throw, a rejected `Promise`, an erroring Observable or this empty completion is a failure.
