# CNGX2032

## A field control also bound by hand

This warning is emitted when the control of a `cngx-form-field` is synced by the field and also bound to the field value by hand, usually `[(value)]="f.x().value"`. `cngx-form-field` already syncs the value atoms of `@cngx/common/interactive` (checkbox, toggle, interactive chip, the radio, checkbox, button-toggle and chip groups), and every control built on `createFieldSync` (the select family, `cngx-rating`, the slider bridges). The hand binding writes first, through `value.set`, which is a programmatic write. The field never sees a user change: it stays pristine, `form().dirty()` stays `false`, an `onDirty` error strategy never shows the error, and a schema `debounce()` is skipped. The model value itself is right.

```html
<!-- WARNING: the click reaches f.terms, but the field stays pristine. -->
<cngx-form-field [field]="f.terms">
  <cngx-checkbox [(value)]="f.terms().value">I accept the terms</cngx-checkbox>
</cngx-form-field>
```

### Fixing the warning

Remove the binding. The field syncs the control in both directions:

```html
<cngx-form-field [field]="f.terms">
  <cngx-checkbox>I accept the terms</cngx-checkbox>
</cngx-form-field>
```

The same goes for `[(selected)]` / `[(selectedValues)]` on a chip or group, and `[(value)]` on `cngx-select`, `cngx-rating` or a slider with `cngxSliderFieldBridge`. A `(valueChange)` handler that writes the model by hand has the same effect.

### Why the field does not treat the hand write as a user change

The field cannot tell a hand binding from any other programmatic write, such as `reset(value)` or loading a model. Turning those into user changes would dirty the field on every reset. The field marks the control's own changes as user changes; a second writer on the same value bypasses that.

### Debugging the warning

The message starts with `CNGX2032: [cngx-form-field]` followed by the field path. The check runs in development mode only, once per field, when the control reports a change the field already holds and the field did not push that value into the control itself. A one-way `[value]="f.x().value()"` warns on the next external write to the field, and a handler that writes the same value into the field in the same tick as a click warns too. Reactive Forms (`formControl` / `formControlName`) and `[formField]` keep their own sync and never warn. In production the warning is stripped.
