# Localisation

<aside class="cc-tldr">

One data file per language, one call in the app config: `provideCngxI18n(withPack(pack))`. CNGX ships the English template (`@cngx/core/i18n/en`) and a German pack (`@cngx/core/i18n/de`). Setting the pack Signal switches every string, number, plural, `<html lang>` and `<html dir>` at runtime. Per-token overrides stay as a second layer on top of the pack.

</aside>

Every user-facing string CNGX renders comes from a section of the active language pack, English when no pack is set. CNGX does not extract messages at build time and has no loader: your app imports a pack and sets a Signal. Two guards keep it honest, both run by `npm run test:scripts`: a hardcoded string outside an English section fails the suite, and every shipped pack must cover every English key with the same placeholders.

---

## Language files

### One call

```ts
import { signal } from '@angular/core';
import { provideCngxI18n, withPack, type CngxCompleteLanguagePack } from '@cngx/core/i18n';

export const languagePack = signal<CngxCompleteLanguagePack | undefined>(undefined);

bootstrapApplication(App, { providers: [provideCngxI18n(withPack(languagePack))] });
```

`undefined` means English. A pack is a plain data object: `locale` (a BCP 47 tag), an optional `dir`, and one section per CNGX area. Each CNGX entry adds its section to the pack type, so the type asks for every area in your code's type graph: the entries you import and the areas they build on. A pack that misses a key fails to compile. `withPartialPack(...)` accepts gaps and reads English for every missing key, and for every key set to `undefined`.

The compile check needs TypeScript to resolve `@cngx/core` from every installed `@cngx/*` package, which a normal install guarantees. A layout where it cannot, such as `npm link` or a symlinked build output, drops the sections without an error under `skipLibCheck`, and the pack then checks nothing.

### Shipped packs

|Entry|Export|Contents|
|-|-|-|
|`@cngx/core/i18n/en`|`CNGX_LANGUAGE_EN`|Every CNGX section in English, generated from the libraries' English sections. The template for a new language.|
|`@cngx/core/i18n/de`|`CNGX_LANGUAGE_DE`|Every CNGX section in German.|

Both are plain data and import no library, so a pack you never load costs nothing. Adjust a shipped pack by spreading it:

```ts
import { CNGX_LANGUAGE_DE } from '@cngx/core/i18n/de';

export const de = {
  ...CNGX_LANGUAGE_DE,
  select: { ...CNGX_LANGUAGE_DE.select, empty: 'Nichts gefunden' },
};
```

### Your own language

Copy `CNGX_LANGUAGE_EN` into `src/i18n/<lang>.ts`, set `locale`, translate the values and keep every key and every `{placeholder}` name. Delete the sections of entries your app does not use; with `satisfies` the compiler names both a missing key and a section your app has no entry for:

```ts
// src/i18n/fr.ts
import type { CngxCompleteLanguagePack } from '@cngx/core/i18n';

export default {
  locale: 'fr',
  card: { selected: 'Sélectionné', deselected: 'Désélectionné', loading: 'Chargement', timestamp: '{prefix} {date}' },
  // ... every other section your app imports
} satisfies CngxCompleteLanguagePack;
```

`card.timestamp` and `paginator.range` stay strings in every pack: their placeholders render as elements, so a plural object or a function does not fit there.

### Loading and switching

The pack Signal is the whole mechanism. Load a pack with your own dynamic import and set the Signal once it has arrived: the current pack stays active until the new one is complete, and the module cache keeps every pack you have loaded.

```ts
const packs = {
  de: () => import('@cngx/core/i18n/de').then((m) => m.CNGX_LANGUAGE_DE),
  fr: () => import('./i18n/fr').then((m) => m.default),
};

export async function useLanguage(lang: keyof typeof packs | 'en'): Promise<void> {
  if (lang === 'en') {
    languagePack.set(undefined);
    return;
  }
  try {
    languagePack.set(await packs[lang]());
  } catch {
    // The current pack stays active; report the failed load your own way.
  }
}
```

**Start language.** Set it before bootstrap, or in your own `provideAppInitializer(() => useLanguage(startLanguage))`. An app initializer also runs on the server, so a server render starts with the right pack.

**Failed load.** A rejected import leaves the Signal untouched, so the app keeps its current language. Retrying is calling `useLanguage` again.

### Messages

A section key holds one of three shapes, all plain data:

- A sentence with `{name}` placeholders: `"Step {position} of {count}"`. A language may reorder the placeholders but never renames them.
- A plural object, picked by `Intl.PluralRules` for the pack's locale from the `count` argument. `other` is required and covers every form a message leaves out; `zero`, `one`, `two`, `few` and `many` are optional.
- A record keyed by a value, for a distinction by case: `{ "online": "online", "busy": "beschäftigt" }`.

German needs two forms, Arabic all six:

```ts
// de
rowsSelected: { one: '{count} Zeile ausgewählt', other: '{count} Zeilen ausgewählt' },

// ar
rowsSelected: {
  zero: 'لم يتم تحديد أي صف',
  one: 'تم تحديد صف واحد',
  two: 'تم تحديد صفين',
  few: 'تم تحديد {count} صفوف',
  many: 'تم تحديد {count} صفًا',
  other: 'تم تحديد {count} صف',
},
```

A number inserted into a message is formatted for the pack's locale (`1.200` in German). An inserted string is wrapped in Unicode isolates (U+2068 / U+2069), so a name in another script keeps its own direction inside the sentence. A pack written in TypeScript may use a function for a message the data shapes cannot express.

### Locale, direction, `lang` and `dir`

The pack drives `CNGX_LOCALE` (its `locale`) and `CNGX_DIRECTION` (its `dir`, else derived from the locale), and CNGX writes `<html lang>` and `<html dir>` from it. One switch flips copy, number format, plural rules, layout direction and arrow-key direction in the same pass: an Arabic pack lays the app out right to left without a `dir` key.

- **Regional formats.** Spread the pack: `{ ...CNGX_LANGUAGE_DE, locale: 'de-CH' }` keeps the German copy and formats `1’200`.
- **App-owned attributes.** If your app sets `lang` and `dir` itself, pass `withDocumentLanguage('off')`; `CNGX_DIRECTION` then keeps reading `dir` from the DOM.
- **Explicit locale.** A `provideLocale(...)` or `provideDirection(...)` listed after `provideCngxI18n(...)` wins.

### Partial packs

`withPartialPack(pack)` takes a pack with gaps: a missing section, a missing key or a key set to `undefined` reads English, and inside a nested record (the stepper `statusLabels`, the feedback `announcements`) each missing key reads its English value. Use it while a translation is in progress; `withPack` is the complete-pack check for production.

### One pack per app

Call `provideCngxI18n(...)` once, in the app config; a second call in route or component providers is not supported. A subtree changes its copy through the per-token overrides below, and its number format through `provideLocaleAt(...)`.

## Per-token overrides

The second layer. Every area keeps its token and its `provide*` / `with*` features, and they apply on top of the pack, key by key, also in a subtree. Reach for them to change a few strings for one app or one subtree without forking a pack:

```ts
provideTabsI18n(withTabsI18nLabels({ tabsLabel: 'Bereiche' }))
```

Unset keys keep the pack's value. There is no all-or-nothing bundle to fill in.

### Resolution order

Every user-facing string resolves `input ?? override ?? pack`. An explicit binding on the instance wins, else a per-token override, else the active pack's section, else English.

A per-instance input alone does not count as translatable, and neither does a default copied out of the token when the component is created. Every input that renders copy is declared `input<T | undefined>(undefined)` and resolved against the token in a `computed()`, so `undefined` means unbound and nothing is read at construction. Sketched for a hypothetical `AppAlertRegion` built on the feedback token:

```ts
private readonly i18n = inject(CNGX_FEEDBACK_I18N);
readonly landmarkLabel = input<string | undefined>(undefined);
protected readonly resolvedLandmarkLabel = computed(
  () => this.landmarkLabel() ?? this.i18n().alertsRegionLabel,
);
```

Bind `[landmarkLabel]` and the binding wins; leave it unbound and the token decides, for the whole lifetime of the instance. When the pack or an override Signal changes, the unbound label changes with it. Reading `instance.landmarkLabel()` returns what the consumer bound, not the resolved text.

One input keeps the default it read at creation: `CngxPhoneInput.country`, a two-way `model<Country>` whose unbound default region comes from the locale. Widening it would break `[(country)]` bindings to `Country`-typed fields. The country name it shows still follows a locale switch.

**Composed copy is a function on the token.** A token key with a count, a plural or an "X of Y" is a `(params) => string`, so an override that needs logic beyond the message shapes writes it out:

```ts
provideFeedbackI18n({
  announcements: {
    alertOverflow: (count) =>
      count === 1 ? '1 weiteren Hinweis anzeigen' : `${count} weitere Hinweise anzeigen`,
  },
});
```

A component never concatenates a translated word with a number; the message or the function owns the word order.

### Scoping to a subtree

Every provider is an ordinary Angular provider, so a component's `viewProviders` scopes it to that subtree:

```ts
@Component({
  viewProviders: [provideDialogConfigAt(withDialogLabels({ close: 'Fermer' }))],
})
export class FrenchSection {}
```

Areas that ship a `provide*At` variant name it explicitly; the rest work the same way because the token resolves through the element injector.

### Signal overrides

Every `provide*I18n(...)`, `with*I18nLabels(...)` and `with*Labels(...)` takes a value or a `Signal` of one; `withAccordionLabels` takes a `Signal<string>` per key. An override Signal follows its own source, independent of the pack, and an empty override means "the pack's value". Overrides merge exactly as they do with plain values: a partial merges key by key, a nested bundle such as the feedback `announcements` or the stepper `statusLabels` merges per key, and a `provide*At` in a subtree resolves against the same base.

Three helpers in `@cngx/core/utils` carry the mechanism, and a hand-written feature or a custom component uses the same ones: `coerceSignal` (value or Signal to Signal), `createOverrideMerge` (defaults merged with partial overrides as one memoized `computed()`) and `createNestedOverrideMerge` (the same, with one nested record merged key by key).

## The flip rule

A language change re-renders every label, name, description and placeholder at once. It never changes what a live region already says: a region keeps its text until its next status change, which then speaks the new language, so a switch never re-announces a stale status. Shown validation messages in `cngx-field-errors` and `cngx-form-errors` are live regions too; they stay in the old language until the field's errors change. A consumer formatter that reads a language Signal itself, such as an error-message function, follows the same rule, because CNGX calls it untracked inside the live region.

## Locale

`CNGX_LOCALE` (`@cngx/core/utils`) is the one locale every CNGX number and date is formatted with. The pack sets it; without a pack, set it with `provideLocale(...)` at bootstrap or `provideLocaleAt(...)` in a subtree's `viewProviders`; both take a string or a `Signal<string>`. Components read it through `injectLocale()`.

```ts
const lang = signal('de-DE');
bootstrapApplication(App, { providers: [provideLocale(lang)] });
```

- **Precedence.** The nearest `CNGX_LOCALE` provider wins, even over a closer `LOCALE_ID`. Without one, the nearest `LOCALE_ID` applies, so an app that provides only `LOCALE_ID` formats exactly as before. `CngxNumericInput`'s `[locale]` input and `withNumericDefaults({ locale })` still win for that input.
- **Angular pipes.** `DatePipe`, `DecimalPipe`, `PercentPipe`, `CurrencyPipe` and `I18nPluralPipe` read `LOCALE_ID`, not `CNGX_LOCALE`. CNGX templates use none of them; an app that switches `CNGX_LOCALE` at runtime owns its own pipe usage.
- **Sort and search.** Label matching folds case and accents with the locale, and the treetable sort collates with an `Intl.Collator` of the reading site's locale.
- **Mid-edit flips.** A locale flip while a numeric input is focused applies on blur: the typed text is parsed in the locale it was typed in. A filled date mask keeps its digits and re-reads them in the new field order; re-set the value if the order changed.

Upgrading from a release where the tokens resolved at construction: see the [localisation migration](./i18n-migration.md) for every changed type and its replacement.

## What is not in scope

`$localize` extraction is not part of the contract, and CNGX ships no languages beyond English and German. Component copy a consumer authors - option labels, titles, route labels, messages - was never CNGX's to translate. Angular's locale pipes and Material's own intl classes (`MatPaginatorIntl`, `MatStepperIntl`) follow `LOCALE_ID` and their own services, not `CNGX_LOCALE` or the pack; the CNGX announcements next to them come from the pack.
